Trunq handbook

Connect to PostgreSQL, write your first query and understand the result. Start here, then explore the tools for working with data and making safer changes.

PostgreSQL 13–18macOS · Windows · LinuxFree & open source

Install Trunq →Download for macOS, Windows or Linux. Run your first query →Connect, check your server and get a result. Stay out of trouble →How Trunq protects your databases.

Install

Download the latest version from the Releases page and choose the file for your system:

SystemFileHow to install
macOS 11+ (Apple Silicon & Intel)Trunq-<version>-macos-universal.dmgOpen it and drag Trunq to Applications.
Windows 10 / 11 (64-bit)Trunq-<version>-windows-x86_64.zipUnzip it and run Trunq.exe.
Debian / Ubuntu (64-bit)trunq_<version>_amd64.debsudo apt install ./trunq_<version>_amd64.deb
Other Linux (64-bit)trunq-<version>-linux-x86_64.tar.gzUnpack it and run ./trunq.
macOS says it "can't be opened because it is from an unidentified developer"? Right-click Trunq.app → Open once. After that it opens normally.

Every release includes SHA-256 checksums in SHA256SUMS.txt. Compute your download's SHA-256 with sha256sum on Linux, shasum -a 256 on macOS or Get-FileHash -Algorithm SHA256 in PowerShell, then compare the matching filename. If you'd rather compile Trunq yourself, see Build from source.

Nightly builds

The Release workflow builds the latest default-branch source every day at 02:00 UTC (03:00 in Paris in winter, 04:00 in summer), once the workflow is merged into that branch. GitHub may delay scheduled runs. Maintainers can also run it manually with the tag input nightly.

Snapshots appear as separate nightly prereleases for macOS, Windows and Linux. They keep the stable download channel separate. Each release identifies its date, workflow run and commit, and includes BUILD_INFO.txt and SHA256SUMS.txt.

Use a separate workspace or back up your settings before trying a snapshot. The app may display its Cargo source version; use the asset filename or build information to identify the nightly. See the nightly installation guide for package names and returning to stable.

Your first connection

  1. Click New connection (or the plug icon in the top bar).
  2. Paste a connection URL such as postgres://user:pass@db.example.com:5432/app?sslmode=require and press Apply, or fill in the host, port, database and user yourself.
  3. Press Test connection, then Save. Choose an environment for the connection. Production appears in red, including a strip above the editor, so you always know where you are.
  4. Browse your database. The connection appears in the sidebar. Expand it to see databases, schemas, tables, views, functions and types. Double-click a table to open its data, or right-click anything for more actions.
  5. Write a query. Press ⌘T for a new SQL editor, then ⌘⏎ to run the statement under the cursor.

Check your connection

Paste this read-only query into the editor and press ⌘⏎. It works on any PostgreSQL database, without the sample data.

SELECT current_database() AS database,
       current_user AS username,
       version() AS server_version;

You should see one row with your database, username and PostgreSQL version. Check the connection identity in the bottom bar before running queries that change data.

Passwords are saved in your operating system's keychain, never in plain text.

Want something to play with? The repository includes a sample shop database with customers, orders, a million analytics events, views, functions and JSON: 
createdb shop
psql -d shop -f dev/sample.sql

Connection options

Trunq speaks the PostgreSQL protocol directly and supports the usual ways of connecting:

  • Encryption (TLS): disable, prefer, require, verify-ca and verify-full.
  • Sign-in methods: SCRAM-SHA-256, MD5 and trust.
  • Unix sockets: enter the socket directory (for example /tmp) as the host.
  • ~/.pgpass: picked up automatically.
  • Connection URLs: paste a postgres:// URL and Trunq fills in the form.

Choose the TLS checks you need

ModeEncryptionCertificate / hostname checks
disableNo PostgreSQL TLSNeither
prefer (default)TLS if accepted; plaintext if the server declines TLSNeither
requireRequiredNeither
verify-caRequiredCertificate trust through the platform store
verify-fullRequiredCertificate trust and database hostname

require encrypts but does not verify the server's identity. A private CA needs trust configured in the platform store; the dialog has no per-profile CA-file or client-certificate selector. Inside SSH, the hostname checked is still the database Host. Local Unix sockets use socket permissions and PostgreSQL authentication rather than TLS negotiation.

Passwords, URLs and pgpass

A supplied session password takes precedence over a saved keychain password, then Trunq tries the first matching entry in ~/.pgpass or PGPASSFILE. Password-file fields are host:port:database:user:password; the first four support *, and literal colons/backslashes need escaping. Protect the file because its passwords are plaintext.

URL import reads the user, password, host, port, database and sslmode. Other query parameters are not applied; set timeouts, read-only mode and SSH in the form. Percent-encode reserved characters and put IPv6 hosts in brackets. Editing a profile affects new sessions; reconnect open tabs to use its changes.

Per-connection safety settings

  • Environment: label the connection LOCAL, DEV, TEST, STAGING or PRODUCTION. Production is shown in red.
  • Read-only: sets default_transaction_read_only=on; database role privileges remain the access control.
  • Statement timeout: a positive value limits statement duration; 0 adds no profile-specific limit. The connect timeout defaults to 10 seconds.

SSH tunnels

Reach PostgreSQL through a bastion or jump host without opening the database to the internet.

  1. Open New connection → SSH tunnel and enable Connect through an SSH server.
  2. Enter the SSH host, port and user. Choose your SSH agent, a private key file or password authentication.
  3. Set the database host and port as seen from the SSH server. Use localhost when PostgreSQL runs on that server.
  4. Test the connection and save it. Connections to the same server share one SSH session.

Trunq checks host keys against ~/.ssh/known_hosts and its own known-hosts file. A new host is recorded on first use. If a host key changes, verify the new fingerprint with your administrator before removing the old entry.

Azure & Microsoft Entra ID

Azure Database for PostgreSQL accepts a short-lived (about one hour) Entra access token as the password. Trunq gets this token and refreshes it automatically before every new connection, so you never have to paste tokens by hand.

  1. Create a new connection with a host such as myserver.postgres.database.azure.com. Trunq recognises Azure hosts and sets SSL to require.
  2. Set Authentication to Microsoft Entra ID.
  3. Choose the Azure cloud. Trunq detects it from the host name:
    • Azure (global): *.postgres.database.azure.com
    • Azure China (21Vianet): *.postgres.database.chinacloudapi.cn
    • Azure US Government: *.postgres.database.usgovcloudapi.net
  4. Pick a sign-in method:
    • Interactive (browser): opens the Microsoft sign-in page. After the first sign-in, the refresh token is kept in your keychain and new tokens are created silently for about 90 days.
    • Device code: for machines without a browser (remote desktops, SSH). Trunq shows a code to enter at microsoft.com/devicelogin or the China equivalent.
    • Azure CLI: reuses your az login session. For China, run az cloud set --name AzureChinaCloud first.
  5. User: your Entra user principal (for example jane@contoso.com) or the name of the Entra group or role that was granted access. Leave it empty to use the signed-in account.
  6. Optional: a Tenant (contoso.onmicrosoft.com or a tenant ID). Under Advanced you can set your own client ID if your organisation blocks the Azure CLI public client.

Writing queries

The SQL editor understands PostgreSQL and helps you as you type.

  • Smart autocompletion for tables, columns, schemas, functions and keywords. It understands aliases: typing o. suggests the columns of orders o.
  • Run what you need: the statement under the cursor (⌘⏎), the selection, or the whole script (⇧⌘⏎). Each result opens in its own tab.
  • Clear errors: mistakes are underlined at the exact position PostgreSQL reports.
  • Parameters: write WHERE id = :id and Trunq asks for the value. Values are remembered per tab.
  • Handy editing: formatter, comment toggle, indent and outdent, and duplicate line.
  • Files & history: open and save .sql files (or drop them on the window), search your query history, and your workspace is restored when you restart.
  • Messages: notices and NOTIFY events appear in the Messages tab.

Use bound parameters

Write :name for a value you want to supply when the query runs. Repeated names share one value; PostgreSQL receives bound parameters, not pasted SQL.

SELECT id, full_name, country
FROM shop.customers
WHERE country = :country
ORDER BY id
LIMIT 100;

This example uses dev/sample.sql. Enter NL when prompted, without SQL quotes. Save frequently used queries as snippets from the editor menu.

Enter parameter values without SQL quotes. Empty input sends empty text; trimmed input NULL, ignoring case, sends SQL NULL. Add a type cast when PostgreSQL cannot infer a parameter's type. Templates using ? need that marker replaced; use :name to request a value. History records executed SQL rather than its parameter values, so keep reusable named queries as snippets or SQL files.

Choose what runs

ActionWhat happens
RunRuns the selection, or the statement under the cursor.
Run allRuns the whole script. Each result gets its own tab.
ExplainShows the query plan. Explain Analyze actually executes the statement.
Dry runRuns an INSERT, UPDATE or DELETE inside a transaction, shows affected rows and rolls back.

Working with results

Results load in pages while database work runs in the background. The grid draws the visible cells; query speed still depends on your server and SQL.

  • Streaming: the first page contains up to 1,000 rows and more load as you scroll. Server execution still depends on the query and database.
  • Virtualised grid: sticky headers, row numbers and resizable or auto-fit columns keep large results navigable.
  • Spreadsheet-style selection with live Σ / avg / min / max of the selected numbers.
  • Search and sort the loaded rows. A table's filter bar applies a WHERE clause on the server.
  • Copy or export as TSV, CSV, JSON, Markdown, SQL INSERT statements or an IN (…) list.
  • Follow foreign keys: ⌘-click a foreign key value to jump to the row it points to, in any result.
  • Value viewer with pretty-printed JSON.

Export the rows you mean

Export optionIncluded rows
Visible rowsThe loaded rows that match the current search, filters and sorting.
Loaded rowsAll rows fetched so far, even if hidden by a local search.
Entire result from the serverRuns the query again on a separate connection and streams every row to the file. Changes since the original query may appear.

Entire-result export runs the SQL again, including any side effects. The destination is replaced only after success; a cancelled or failed export preserves an existing file. In CSV, SQL NULL is an unquoted empty field and empty text is "".

File scopes choose rows; hidden columns are still included. Select the required columns in SQL for a narrower file. Save pending table edits and refresh before exporting saved values. An entire-result export cannot see the tab's temporary tables, session-local settings or uncommitted changes because it uses another connection.

Paging and pinned results

Only the final statement in a run keeps a fetchable cursor. Run a large SELECT by itself when you need to keep loading pages. Pinning retains the rows already loaded; another run closes the previous cursor, and pinned rows are not restored after the app exits. Fetch or export what you need first.

Compare and inspect

Pin a result to keep it when you run another query, then use the side-by-side view. Select two to six rows to compare their differences, or open card view to read a wide record vertically. Open a JSON value for a searchable tree with copyable paths.

Editing data

  1. Double-click a table to browse it. Use the WHERE / ORDER BY bar to narrow it down. Key icons mark the primary key.
  2. Edit cells inline, or add, duplicate and delete rows, and set values to NULL. Changed cells are highlighted.
  3. Preview the generated SQL, then save everything in one transaction.

If a statement fails, that save is rolled back and pending edits remain available to fix and retry. Within an existing explicit transaction, Save uses a savepoint and leaves the transaction open for you to commit or roll back.

Auto-commit, Manual and failed transactions

Manual starts a transaction before running SQL when needed. Use Commit to retain its changes or Rollback to discard them. Switching the selector does not finish an already-open transaction. Transactions belong to one tab; disconnecting loses its uncommitted work.

After an error in an explicit transaction, Transaction failed means you must roll back before normal SQL can continue. Find the original error earlier in Messages. A paged SELECT can also show In transaction while its cursor remains open; finish fetching or close its session when it is no longer needed.

Charts

Turn any result into a chart, choose X and numeric Y columns, and use Auto, Bars or Lines. Auto uses lines for time/numeric X values and bars for categories. Default series selection favours similar scales; selecting very different scales shows a warning.

Charts use loaded result rows independently of grid search/filter chips. They do not aggregate for you. Filter and GROUP BY in SQL first, then choose the axes. Up to eight series are selectable; bars display at most 300 rows.

SELECT status, count(*) AS orders, sum(total) AS revenue
FROM shop.orders
GROUP BY status
ORDER BY status;

This example uses dev/sample.sql. Plot order counts and revenue separately when their scales differ.

Importing CSV files

Drop a CSV or TSV file onto the window. Trunq works out the delimiter, header, column names and column types (integer, bigint, numeric, boolean, date, timestamptz, uuid, jsonb).

Create a new table or add to an existing one. The data is streamed in a single transaction with live progress, which is the fastest way to load data into PostgreSQL.

Check the preview before importing: it reads up to the first 1 MiB and infers types from up to 2,001 records, including a header when enabled, so later values may need a wider type. Quoted delimiters and timezone offsets are supported, and colliding header names receive unique suffixes. For an existing table, verify every mapping: initial mapping tries names, then positions. Empty it first truncates that table within the import transaction. Errors and cancellation roll back the import.

Use UTF-8 CSV/TSV. PostgreSQL COPY CSV treats an unquoted empty field as NULL and a quoted empty field as empty text. The preview does not distinguish them as separate inferred types. A literal NULL field is text, subject to the target column's type.

ER diagrams & metadata

Right-click a database, schema or table and choose ER diagram, or find it in the command palette. Diagrams reuse the loaded catalog, so opening one needs no additional database query.

Pan, zoom, drag tables, inspect columns and keys, or export SVG and Mermaid. Opening from a table focuses its neighbourhood; opening from a schema limits the graph to that schema.

Inspect the catalog

Expand a table for its indexes, constraints, triggers and policies. Hover for index methods, validity, constraint definitions and trigger functions. An RLS indicator marks enabled row security. Server-level Roles and Tablespaces show attributes and ownership; right-click a role to copy its DDL.

Find expensive statements

Right-click a database → Slow queries (pg_stat_statements). Review and run the generated SQL to inspect calls, execution time, returned rows and buffer/temp-block counters. Your DBA must preload and install pg_stat_statements; Trunq does not change the server configuration. Access to other users’ query text depends on your role.

Docker & Docker Hub

The Docker image runs the native client in a browser-accessible noVNC desktop. Use a native release for maximum interactive performance: the container adds software rendering and desktop streaming.

docker compose up --build -d

Open localhost:8080/vnc.html. The virtual screen scales to your browser window. The Compose file keeps the workspace in a volume and publishes only on loopback. The desktop has no built-in authentication; keep that binding for local use or use an SSH tunnel for remote access. Connect to host PostgreSQL via host.docker.internal.

Publish your image

Configure the repository variable DOCKERHUB_USERNAME and secret DOCKERHUB_TOKEN. The Docker workflow builds and smoke-tests the desktop before publishing amd64 and arm64 images on version tags or an explicit manual run. Stable version tags update latest; manual runs publish a commit tag.

See the full Docker guide for manual Buildx commands, the native target, credentials and remote access.

Performance you can measure

Trunq pages results through PostgreSQL portals and draws visible grid cells. Empty searches and selection aggregates stay cached until the relevant data, view or edits change. Search, sort and hidden empty columns include pending edits.

cargo test --release --locked bench_empty_filter_million -- --ignored --nocapture
TRUNQ_TEST_DATABASE_URL=postgres://… cargo test --release --locked bench_fetch_million -- --ignored --nocapture

Fetching, server execution and drawing are different costs. A fast first page is not a guarantee that any query will execute quickly. The performance report describes the workload and measured limits; the research notes distinguish shipped features from future PostgreSQL integrations.

Finding your way around

  • Command palette (⌘K): fuzzy-jump to any table, view, function, connection or command.
  • Object tree: databases, schemas, tables (expand to see columns, keys and foreign keys), views, materialized views, sequences, functions and types, with row estimates and sizes.
  • Generate SQL from the right-click menu: SELECT / INSERT / UPDATE / DELETE, DDL, function definitions and maintenance commands.
  • Query plans: EXPLAIN and EXPLAIN ANALYZE are shown visually, with each step's share of the time, loop counts and row-estimate warnings.

Safety features

Trunq is designed to help you avoid the mistakes that cause outages.

Lock detective

When a query has been running for more than 1.5 seconds, Trunq shows what it's waiting for and which session is blocking it, including the user, application, query and transaction age. One click cancels that session's query or terminates the session.

Dry run

Press ⌥⌘⏎ to preview an INSERT, UPDATE or DELETE. Trunq uses a transaction or savepoint and rolls back before reporting completion, preserving an existing explicit transaction. Returned-row previews are limited by the fetch page. Sequences and external side effects of server functions are not generally undone by rollback. EXPLAIN ANALYZE executes its query; plain EXPLAIN plans it.

Migration linter

Before running a change that would block or rewrite a table, Trunq explains the risk and the safe alternative. Plain CREATE INDEX statements get a one-click Add CONCURRENTLY fix. Trunq checks for:

  • Plain CREATE INDEX
  • Column type changes
  • SET NOT NULL
  • Foreign keys without NOT VALID
  • Volatile defaults
  • VACUUM FULL

Confirmations & guards

  • Trunq asks before running an UPDATE or DELETE without WHERE, a DROP, or a TRUNCATE.
  • Forgotten-transaction guard: a banner appears when a tab has held a transaction (and its locks) open for more than a minute.
  • Live progress for CREATE INDEX, VACUUM, ANALYZE, COPY and CLUSTER.

Health check

One click finds the problems that cause real outages. Each finding comes with generated fix SQL for you to review, and nothing runs automatically.

  • Integer IDs close to running out
  • Transaction-ID wraparound
  • Inactive replication slots filling the disk
  • Foreign keys without indexes
  • Invalid, duplicate or unused indexes
  • Bloated or never-analyzed tables
  • Long-running transactions
  • Tables without a primary key
  • Low cache-hit ratio

Connection management

Trunq never leaks connections.

  • Every connection belongs to exactly one tab or sidebar item, and closes when that goes away. A running statement is cancelled first.
  • Idle query tabs disconnect after 15 minutes and reconnect transparently when you come back.
  • The status bar shows the live connection count. Click it to see every connection (purpose, PID, age) and close any of them.
  • Each connection sets application_name (for example Trunq: Query 3), so you can find it in pg_stat_activity.
  • Background metadata connections use lock_timeout and statement_timeout and never take table locks, so they can't get stuck behind a migration.
  • TCP keep-alive detects dead networks, and everything is closed cleanly on exit.

Start a separate workspace

Set TRUNQ_CONFIG_DIR before launching. It changes settings, history and Trunq's SSH known-hosts location, but does not create a separate OS keychain. Copied profiles keep their IDs and can still refer to the same keychain entries on that computer.

TRUNQ_CONFIG_DIR="$PWD/trunq-workspace" trunq

The example is for macOS/Linux with Trunq on PATH. Windows PowerShell uses $env:TRUNQ_CONFIG_DIR = Join-Path $PWD 'trunq-workspace' before starting the executable.

Back up and restore

  1. Finish or roll back transactions, save table edits and SQL files, and export any result rows you need.
  2. Close Trunq, then copy the settings directory, including config.json, history.jsonl and known_hosts when present.
  3. Copy external SQL files and exports separately. Restore the settings directory while Trunq is closed, then recheck hosts, labels and key paths.

Loaded results, pinned rows, pending edits and open transactions are not restored. Copying this folder does not transfer the OS keychain, SSH private keys or Azure CLI login, and is not a backup of database data. SQL text/history can contain sensitive literals and comments; review files before sharing them.

Use a new empty workspace to try clean settings, or rename the existing directory while the app is closed so you can recover it. Query history → Clear clears history, not snippets or editor text. See settings and backup details.

Troubleshooting

"password authentication failed" or "no password supplied"
Type the password in the field that appears in the sidebar or above the editor. It's remembered for the session, and saved in the keychain if Save in keychain is on.
Azure: AADSTS… errors
Check the tenant, check that your account (or its group) was added as an Entra admin or role on the server, and check that the right cloud is selected. If your organisation's policy blocks the browser flow, try Device code.
The app window is blank on an old GPU or virtual machine
Start Trunq with WGPU_BACKEND=gl to use OpenGL.
Keychain prompts on macOS
Click Always Allow once so Trunq can read its saved passwords.
"current transaction is aborted"
Find the original statement error in Messages, choose Rollback, then correct and retry it. Switching Manual/Auto-commit does not finish the transaction.
The table is read-only or Save fails
Use a table view with a primary key, check the profile's read-only setting and database permissions, then inspect constraints in the error. Duplicate row omits generated/key fields, but another unique value may still need changing.
Search, charts or exports show unexpected data
Check loaded rows versus server data, remembered filters, hidden columns and pending edits. Charts use loaded rows independently of grid filtering; file exports include hidden columns. Entire-result exports cannot access a tab's temporary tables or uncommitted changes.
CSV works in preview but fails later
Inference samples the start of the file. Review later values, widen the target type, and check header, delimiter, mapping and constraints. The import rolls back on error.
Settings or tabs disappeared
Check the account and TRUNQ_CONFIG_DIR. A missing or malformed configuration loads defaults; close the app and preserve an existing file before recovery. Loaded result data is not saved with tabs.
macOS won't open the app
Right-click Trunq.app → Open once, or run xattr -dr com.apple.quarantine /Applications/Trunq.app.

See the full troubleshooting guide for connection, TLS, SSH, transaction, import and workspace checks. When opening an issue, include version/commit, OS, PostgreSQL version, exact error and minimal steps; redact secrets and sensitive query data.

Build from source

You'll need Rust 1.95 or newer. The first build downloads and compiles dependencies and takes a few minutes. Later builds are incremental. Use --locked to keep the repository's dependency versions.

# 1. Install Rust (once)
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"

# 2. Get the code, build Trunq.app and copy it to /Applications
git clone https://github.com/IssamElNass/trunq.git trunq
cd trunq
./scripts/bundle-macos.sh --install

Use ./scripts/bundle-macos.sh to only build Trunq.app, or add --dmg to also create a shareable Trunq.dmg. Requires macOS 11+ and the Xcode command line tools (xcode-select --install).

# Debian / Ubuntu build dependencies
sudo apt install build-essential pkg-config libssl-dev libxkbcommon-dev libwayland-dev

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"
git clone https://github.com/IssamElNass/trunq.git trunq && cd trunq
cargo build --release --locked
sudo install -m 755 target/release/trunq /usr/local/bin/trunq

On Fedora: sudo dnf install gcc pkgconf openssl-devel libxkbcommon-devel wayland-devel. Linux uses Secret Service (GNOME Keyring or KWallet) to store passwords.

Install Rust with the MSVC toolchain, plus the Desktop development with C++ workload from Visual Studio Build Tools and a Windows SDK. Then, in a terminal:

git clone https://github.com/IssamElNass/trunq.git trunq
cd trunq
cargo build --release --locked
.\target\release\trunq.exe

Development

Read CONTRIBUTING.md before opening a pull request.

cargo run              # debug build, fastest to compile
cargo run --release    # optimised build
cargo test --locked    # run the test suite
cargo fmt --all --check
cargo clippy --locked --all-targets -- -D warnings

Database tests need a disposable PostgreSQL server; without TRUNQ_TEST_DATABASE_URL they return without connecting. Set that variable and run cargo test --locked live_tests -- --test-threads=1 to exercise queries, paging, COPY, catalog metadata, table-save recovery, dry-run rollback and exports. SSH live tests additionally require TRUNQ_TEST_SSH. The documentation index links to the installation, user and developer guides.

Scripted UI runs

Load dev/sample.sql into a disposable database and run TRUNQ_TEST_DATABASE_URL=postgres://… python3 scripts/screenshots.py. It captures twelve views in a temporary workspace and converts them to WebP when cwebp is available. TRUNQ_CONFIG_DIR selects an isolated configuration directory.

For visual checks without OS permissions, drive the app with TRUNQ_SCRIPT:

TRUNQ_SCRIPT="wait:3;run;wait:2;shot:/tmp/query.png;open:shop.orders;wait:2;shot:/tmp/table.png;quit" cargo run

Steps: wait:<s>, run, runall, dryrun, explain[:analyze], sql:<text> (separate statements with ;;), open:<schema.table>, tab:<n>, palette:<query>, health, newconn, connections, theme:light|dark, shot:<file.png>, quit. Scripted runs never overwrite your saved workspace.

Nightly automation and package previews

Stable tags and daily nightlies share the Release workflow. It resolves one source commit, runs snapshot unit tests and packages each platform, then assembles checksums/provenance before publication. Nightlies use distinct dated prerelease tags and do not move the stable download channel. A failed platform build does not publish a snapshot.

Pull requests changing packaging produce a release-bundle Actions artifact without publishing or notarizing. Preview artifacts remain for seven days. The schedule runs after the workflow is on the default branch; maintainers can use manual tag=nightly dispatch for a fresh default-branch snapshot. See the maintainer guide.

Releases
